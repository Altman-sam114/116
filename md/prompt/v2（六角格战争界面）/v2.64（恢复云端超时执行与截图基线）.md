## 4. 实现步骤

### 4.1 Python 标准库 timeout wrapper

1. 接口简洁明确，例如 `python3 .github/scripts/run_with_timeout.py <seconds> <command> [args...]`；拒绝非正/非有限超时和缺少命令的调用，输出用法并返回非零。
2. 使用 `subprocess.Popen(argv, start_new_session=True)`，不使用 `shell=True`，保留参数边界；stdout/stderr 继承调用方，使命令输出仍进入现有 stage 日志，不能把大构建日志全部缓存在内存。
3. 用 `wait(timeout=...)` 或标准库等价机制计时；成功/普通非零退出转发真实结果。子进程因信号退出时映射为正常 shell 可理解的非零退出状态，不能被当作成功。
4. 真正超时返回 `124`，日志明确包含命令阶段、限制秒数和 `timeout` 原因；对整个新进程组发 SIGTERM，短暂有界等待后对仍存活的进程组发 SIGKILL，并回收直接子进程。即使组长先退出，也不能留下忽略 TERM 的子孙编译进程继续占用 runner。
5. 可执行文件不存在时返回 `127`，日志明确 `command not found`，不得写成超时；权限不足、启动异常也要保留明确诊断和非零退出码。
6. wrapper 自身收到取消/中断时尽可能终止并回收它创建的进程组，不能向 runner 自身进程组发信号。只控制自己 `start_new_session` 创建的组。
7. 无需泛化成新的 CI 框架；实现保持小而可审核，可用 Python 内置 argparse、subprocess、os、signal、time 等标准库。

### 4.2 Workflow 统一替换和诊断

1. 查找 workflow 内全部裸 `timeout`，包括继承 v2.63 的 swiftc `300` 秒、xcodebuild `900` 秒，以及截图阶段 bootstatus/install/launch；改用同一个 wrapper，保留各阶段既有合理时限，不简单扩大 job timeout。
2. 保留 shell 的退出码读取和 pipefail 行为；wrapper 返回 `124`/`127` 时日志必须能定位“阶段超时”或“缺少命令”，不能被随后 `echo` 覆盖。
3. 调整截图错误摘要：bootstatus 非零不一概声称 Simulator 自身 boot 失败，至少区分 wrapper 超时、命令缺失和实际 simctl 错误；安装、启动同理。详细原始 stderr 保留。
4. 不改 screenshot 场景，不降低至少 500 KB PNG 门禁，不跳过 app 安装/启动，不拷贝历史截图。真实成功仍需要 boot、install、launch 和当前 run 的截图。
5. 保留有限截图重试和 `always()` 打包；失败/超时必须仍能上传 manifest、failure summary 与已有日志，最终 job 非零。不要用全局 `continue-on-error` 把红色检查改绿。
6. static 阶段增加 wrapper 的云端契约检查或独立轻量云端步骤：成功命令返回 `0`；普通失败转发约定的非零（如 `7`）；短 sleep 超时返回 `124`；明确不存在的命令返回 `127`。命令使用 `sys.executable`/当前 `python3` 与标准库，不能为自测引入依赖。检查结果进入日志及总门禁，不能打印通过却忽略失败。
7. 云端执行 YAML 解析、`git diff --check`、项目 `plutil -lint`、Rules smoke 编译/运行、Xcode build-for-testing 和 regular screenshot；本轮 XCTest 执行仍按现有配置，若 skipped 必须照实记录，留待 v3.0 实际执行闭环。
